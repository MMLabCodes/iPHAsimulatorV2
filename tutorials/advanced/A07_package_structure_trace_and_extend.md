# A07 — Read the package and design an extension

**Task:** identify the owners of existing behaviour before proposing new functionality.

**Inputs:** one source module. **Output:** an import/function map and a written extension design. The adjacent script reads Python syntax without importing or executing the inspected module.

## Distinguish three kinds of interface

A public function is a candidate for direct use, an underscore-prefixed helper is an implementation detail, and a workflow coordinates several operations. Naming alone is not a complete compatibility policy. The reference index distinguishes functions, methods, properties, nested helpers and overwritten definitions so readers can see what is actually present.

Dataclasses carry results between modules: examples include loaded simulations, distance descriptors, PCA/clustering results, GROMACS preparation outputs and timing records. Their fields matter as much as function arguments. Each module reference includes class declarations and fields, including classes whose constructors are generated by dataclasses rather than explicitly written.

## Trace an existing workflow

Start at `run_tg_analysis()`. Identify the file lookup, data loading, descriptors, PCA, clustering, fitting, persistence and presentation operations. Follow one result object through those calls. Then compare `run_system_tg_analysis()`, which consumes saved summaries rather than repeating the trajectory calculation.

For database work, distinguish path lookup from initialisation and registry mutation. `PHAFileManager` currently creates directories/registry state when constructed and imports ParmEd. A call that appears to be path inspection can therefore have dependencies and side effects. `PHAResidueCodeManager` owns chemistry-code allocation, not parameter validation.

For system construction, compare the single-chain functions, the melt builder and the Packmol route. Different inputs/outputs justify separate strategies. Their boundaries are described in the reference module guides; do not assume a shared class name means interchangeable capabilities.

## Design exercise: a new analysis

Write down, before coding:

1. The exact question answered and supported system types.
2. Required input files and metadata, with units.
3. Settings that affect the answer.
4. A pure calculation boundary where practical.
5. A result record and versioned output schema.
6. How callers distinguish missing inputs, invalid data, execution failure and success.
7. A small known-input check and an integration example.

As an example, summarising recorded temperature does not require repeating descriptors, PCA or Tg fitting. It can consume a state-data table, return summary statistics, and optionally write a separate result. Do not label it a Tg estimator or copy Tg-specific output keys merely to satisfy a GUI expectation.

## Current discovery limitations

The GUI discovers `analysis/**/workflow.py`, imports a module in the scientific environment, and calls `run_analysis()` or the Tg fallback with system, simulation and figure preference. It also assumes particular output locations and summary fields. System-level analysis currently has a different entry point. A new workflow file alone is therefore not proof of complete GUI integration.

This is an explanation of the existing convention, not a new plugin API. Before implementing an extension, decide which interface changes are required and preserve existing callers deliberately. The workshop does not install example plugins or modify the package.

## Function-level reading and coverage

The [coverage index](../reference/coverage_index.md) accounts for every explicit function definition under `src/iphasimulator`, including nested functions and duplicate definitions. Every entry includes its signature/defaults, the existing docstring when present, source-derived return/error/call information, and an implementation excerpt. Class records and import-only/empty modules are included too.

These entries are a snapshot, not executable tests or independently verified scientific documentation. Missing source documentation is stated rather than invented. Direct-call lists do not resolve dynamic dispatch or prove the absence of side effects in callees. The snapshot manifest records source hashes; regenerate the reference after package changes.

The reference intentionally excludes third-party libraries and GUI functions from its exhaustive count. The GUI is discussed only where it consumes the package. Built-in/generated methods that have no explicit source definition are not counted as hand-written functions.

**Review question:** Why is moving code into another folder insufficient to make it modular? **Answer:** Input/output contracts, dependency direction, state ownership and responsibility boundaries must be clear; directory names cannot establish those properties alone.
